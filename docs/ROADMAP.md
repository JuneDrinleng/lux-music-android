# 原生安卓路线图

状态：提案。优先顺序：架构 → 骨架/门禁 → 功能。[ARCHITECTURE](ARCHITECTURE.md) 是本 PR 核心；mobile 仅作[功能对照](PARITY.md)。本次交付仅文档，不把批准文档 PR 等同于批准任何功能实现。

**第 0 阶段必须先经 June 明确批准，才能开始；第 0 阶段验收通过后才进入功能开发。** 若后续发现核心边界需要改变，回到架构评审，不在功能 PR 顺便引入历史包装。

MVP = 能播放 + 能通过现有 lux-music-server 同步歌单（含两客户端可观察的往返与断线恢复）。只有播放器或只有本地歌单都不算 MVP。歌词、统计、推荐、桌面歌词等不阻塞 MVP。

下表每一行是一份可单独评审的小 PR；实际变大时继续拆。工作量单位均为单人有效开发日的**粗估**，不含等待决策、源站变化和设备供应；不是工期承诺。

| 阶段 / PR | 范围与依赖 | 验收标准 | 工作量粗估 |
| --- | --- | --- | --- |
| 0A 架构定案 | June 决定包名、minSdk、单一数据层、脚本边界、v1 导入策略与门禁 | ADR 记录决定及例外；未批准项不以默认代码固化 | 粗估 1–3 日 |
| 0B 编译骨架 | 批准 0A 后建立 Kotlin/Compose 与架构模块，仅空页面/假实现 | core 纯 Kotlin；依赖图无环且符合白名单；新 applicationId 可与 mobile 两渠道并装；API 33 启动空壳 | 粗估 2–4 日 |
| 0C 门禁与数据骨架 | 依赖 0B；提出 CI 的具体变更再按 PR 审批 | 编译/lint/依赖规则可运行；四种违规样例被拒；Room 事务失败无孤立待办；没有业务功能或迁移器 | 粗估 2–5 日 |
| 0D 协议与脚本可行性 | 依赖 0A；用虚构/脱敏 fixture 和测试宿主，不做功能 UI | message2call 帧、MD5 顺序、压缩/握手向量验证；QuickJS 超时/取消/内存限额验证；绑定许可证/ABI 选择落 ADR。未知项列清，无法终止脚本则阻塞相关功能 | 粗估 3–6 日 |
| 1A 播放服务 | 第 0 阶段全通过；单条受控音频 | Media3 服务播放/暂停/seek；后台、锁屏/通知操作、耳机断开/焦点中断正确；失败能重试 | 粗估 3–5 日 |
| 1B 队列与页面 | 依赖 1A | 同歌可出现两次；上一首/下一首/顺序策略正确；进程重启只由服务恢复一次；UI 不维护第二份实时队列 | 粗估 2–4 日 |
| 2A 搜索与目录端口 | 依赖 1B、0D；先完成一个经确认可用的目录来源 | 有界分页、取消、错误/空态；DTO 不出 data；搜索歌曲可进入队列；不注册 xm 占位源 | 粗估 3–5 日 |
| 2B 自定义音源 | 依赖 2A 与 QuickJS 验证 | 用户选脚本、显示能力；musicUrl 返回可播放结果；请求取消与死循环不挂 UI；无账号凭据/文件越权；增加 lyric/pic 可再拆 PR | 粗估 4–8 日 |
| 3A 本地歌单 | 依赖 2A | 创建/改名/排序/删除、收藏、歌曲增删移动均为 Room 事务；页面重开一致，保留 ID 不误删 | 粗估 3–5 日 |
| 3B 数据恢复与账号空间 | 依赖 3A | 重启恢复、空间切换无串数据；Remote 写入不产生本地待发；v1 没有 RN 私有数据导入路径 | 粗估 2–4 日 |
| 4A 基础歌词（可与 5 并行安排） | 依赖 1B、2B；非 MVP 阻塞项 | 时间轴解析、seek 后对齐、空/错歌词不影响播放；共享歌词模型适配窗口 | 粗估 2–4 日 |
| 4B 扩展歌词 | 依赖 4A | 翻译/罗马音和逐字仅按真实能力展示；格式不支持可降级；悬浮歌词单独评审权限及生命周期 | 粗估 3–6 日 |
| 5A server 账号握手 | 依赖 3B、0D；可提前于阶段 4 | 登录/刷新/退出；稳定 deviceId；领取 key、WS 协商；旧连接不能跨会话写入；不改 server | 粗估 3–5 日 |
| 5B 首次歌单同步 | 依赖 5A | 从非空 server 到全新原生客户端，default/love/userList 顺序与元信息正确；冲突合并/覆盖/取消方向经 fixture 验证；覆盖不静默记忆 | 粗估 3–6 日 |
| 5C 增量与恢复（MVP 门槛） | 依赖 5B | 原生 ↔ server ↔ mobile 创建/改名/排序/歌曲增删往返；重连、超时不确定状态、断电、账号切换无重复/误删/回传环；本地待办最终收敛；播放与同步同时工作 | 粗估 4–8 日 |
| 6A 听歌记录 | MVP 后；先本地行为语义再开启协商能力 | 播放/暂停/跳过/完成生成记录规则明确，ID 去重；push/pull 游标与持久事务一致；未协商不发送 | 粗估 3–5 日 |
| 6B 统计与报告 | 依赖 6A | 本地时区、跨月/跨年、重复记录、未来时间 fixture；月报/年度报告可追溯到记录；分享图为独立 PR | 粗估 3–6 日 |
| 7A 后续能力逐项立项 | 依赖需求决策，参考 PARITY | 下载/本地库、推荐、音效、白噪音、评论、一起听各开 ADR/小 PR；每项先定数据与后台归属，不能整包搬迁 | 每项粗估 3–10 日，立项后细化 |

阶段号表示建议排序，不能为等歌词而推迟 MVP 的同步验证；5A 的契约试验应尽早暴露风险。外部目录/音源的在线可用性不由此文承诺；失败应给出可理解的原因而非引入无限换源链。

## 分支与日后发布（仅提案）

目前仅 `main` + 短期任务分支，通过小 PR 交付。**建议暂不建 dev**，在 MVP 后确有持续试用需求时由 June 决定是否设长期 dev 集成分支。也可继续 main + 独立测试渠道，减少分支漂移。此任务不创建 dev，不重命名 main 为 master。

mobile 的 `.github/workflows/ci.yml` 监听 dev/master，`.github/workflows/release.yml` 实现 dev 预发布、master 稳定版，并含回写发布索引和旧预发布清理逻辑。这只证明参照项目的做法；新仓库不复制自动回写主分支、删 tag/release 或多渠道矩阵。

未来建议分开“PR 验证”和“发布”：验证通过后，由 June 明确选择版本、渠道和签名策略；发布使用同一已验证提交，先构建/测试/校验签名与产物，再按批准触发预发布或稳定版。dev/master 双通道是否采用、稳定分支是否继续叫 main、触发方式、applicationId 后缀、版本号、签名与产物保留均待决定。任何 CI 文件、标签或发布操作都需届时另开任务授权；本 PR 不执行、不预置签名数据、不更改仓库设置。

## June 的决策清单

- 是否批准以 ARCHITECTURE 为基线并启动第 0 阶段（批准本 PR 不自动授权功能实现）？
- 包名 `cn.lux.music.android`、minSdk 33 是否接受？若需支持更旧设备，具体范围是什么？
- 是否批准唯一 Room 数据层、Media3 实时播放状态归属、模块依赖白名单？
- 是否接受 QuickJS 与受限宿主方案，并先做绑定/协议可行性验证？
- v1 默认不导入 RN 本地遗留数据是否确认？有无必须另案论证的例外？
- 是否采用列出的结构、静态检查、契约/设备测试门禁？CI 实施及合入限制另案处理。
- 是否采纳暂不建立 dev，等 MVP 后再决定分支与双通道发布？
- MVP 是否按“可播放 + server 歌单双向同步与恢复”验收，其余能力后置？
