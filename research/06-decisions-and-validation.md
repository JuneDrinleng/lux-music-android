## 建议决策登记（尚未写入正式 ADR）

| 编号 | 建议 | 原因 | 改变它需要的证据 |
| --- | --- | --- | --- |
| A1 | Kotlin/Compose + ViewModel/Flow | 原生生态、精确自定义 UI、生命周期 | 性能/字体/阴影原型无法满足时评估局部自绘，不直接包网页 |
| A2 | 约 7 个初始模块，其余按 package | 隔离协议/播放/源又减少空壳 | 真实构建依赖/协作边界需要更细分 |
| A3 | Media3 服务唯一持有 Player | 后台/锁屏/蓝牙同一条控制链 | 不满足的具体音频特性，不能仅凭样本习惯另造引擎 |
| A4 | Room 为业务资料源，独立 workspace 分库 | 减少账号漏 owner 风险 | 可验证约束覆盖的单库方案有明显收益 |
| A5 | 三类 auth adapter，共用 LX v4 sync | 两 server、Lux 两合同已证实 | 明确不再支持某部署版本；不是猜测“大家已升级” |
| A6 | 源脚本 ABI 隔离兼容，核心原生 | 不牺牲已有源使用能力 | 用户确定不支持旧脚本，或实际 ABI/引擎验证结果 |
| A7 | 多账号本地保留，切换有事务提交点 | 降低重新登录与串资料风险 | 产品明确只支持单账号，仍须处理过期/换身份 |
| A8 | LX 与 local 默认隔离资料 | 缺少稳定远端 userId，减少误同步 | 用户确认继续共享的实际需求与同步风险说明 |
| A9 | main + 短 PR + tag；stable/preview | 降低合并/发版状态空间 | 长期稳定维护或团队工作方式确实需要 dev 分支 |
| A10 | 不移植 RN 补丁/历史迁移与多厂商 flavor | 干净起点、避免长期兼容包袱 | 真实设备问题或明确数据迁移需求 |

## 后续真正需要用户选择的事项

这些目前不阻碍调研完成，不要求现在逐条答复。进入正式方案时优先确认前三项。

1. **业务范围**：HTML 全前端 + mobile 核心功能，是否同时要求一起听聊天/点歌/反应、AI token 管理、管理控制台、白噪声、横屏特殊布局、Android Auto？现有代码存在与 UI 可见不是同一回事。默认研究保留能力边界，不擅自删掉已使用功能。
2. **兼容范围**：本次 LX v4、Lux master/dev 都列入目标；实际部署若是别的 tag/commit，需追加固定基线。服务地址/凭据不写研究文档；联调优先测试部署。
3. **资料策略**：LX 独立资料是否接受？从 RN 导入是否必要？本机资料是否允许显式复制到新账号？默认不自动合并。
4. **新 app 身份**：applicationId、显示名、是否与 RN 并存、发行签名归属；建议默认并存，不覆盖 RN。
5. **设备与渠道**：最低 Android、armv7、厂商、Play/F-Droid/GitHub；建议先 GitHub APK，不能假装已满足所有商店要求。
6. **账号设计**：选定改进流程后，是先更新 HTML 原型还是补独立账号设计状态表？现有示例账号页不足以直接验收真实业务。
7. **复杂功能优先级**：功能总范围与首个可用版本范围需要分开；分期不是最终删功能。

## 测试形态与成本控制

- domain/编解码/账号 reducer 用 JVM tests；数据库隔离/恢复用 Room instrumentation 或适当真实存储测试，不只 mock 所有事务。
- 固定三种 server 快照作为合同基线，golden 数据必须来自实际合同并保留生成来源；不能手写自己期待的返回再证明自己正确。
- 初始用少量代表 API/设备跑 critical flows；定时扩展 OEM/系统版本。真实音频焦点、系统恢复、文件权限不能完全被 UI screenshot tests 代替。
- UI 使用 deterministic fixture、固定字体缩放/逻辑视口和暂停的动效，保留与 HTML 的并排/叠加证据；只需必要 baseline，不为每一段文档写测试。
- 纯研究文档本轮做链接/来源/覆盖核查，不运行 Gradle/服务端测试来制造“全绿”的假象。

## 不增加冗余的验收问题

每个拟新增抽象回答：是否有两个真实调用者或一个需要隔离的外部边界？是否存在唯一状态所有者？去掉它能否仍守住身份/持久化/协议约束？是否只是转发另一方法？有没有到期/删除条件？

需要保留的复杂度是外部协议、媒体生命周期、资料隔离和崩溃恢复；应消除的是重复状态、全局桥接、没有用户价值的多版本双写和提前设计的通用平台。不能把“文件少”当成架构简单，也不能把“模块多”当成架构优秀。
